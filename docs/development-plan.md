# Swanium Crystal 開発計画

## 目的と前提

Crystal で WonderSwan / WonderSwan Color / WonderSwan Crystal を再実装する。対象はエミュレータ本体と、自作・公開許可済みのテストプログラムを実行するための開発環境である。

- [ ] 実装対象を **macOS → Linux** とする
- [ ] Crystal の Windows 対応が正式リリースされるまで、Windows の実装・CI・配布に着手しない
- [ ] 実 ROM の読み込み、配布、暗号化回避、ライブラリ管理を実装しない
- [ ] BIOS、商用ゲームデータなど権利者のあるデータをリポジトリに含めない
- [ ] コアを UI や OS API に依存させず、ヘッドレスでテスト可能にする
- [ ] 開発ツールのバージョン固定と実行を mise で統一する

## 移植の互換性契約

本プロジェクトは新規エミュレータではなく Rust 版 Swanium の Crystal 移植である。したがって、各機能を「似たもの」として再実装するのではなく、元実装が受け入れている検証結果を移植版でも再現する。

- [ ] 元実装の `crates/core` を挙動の基準とし、CPU、メモリマップ、割り込み、タイマ、DMA、PPU、APU、カートリッジ、RTC、保存データの仕様を対応表にする
- [ ] Rust 版のユニットテストおよび統合テストと同等のケースを Crystal の `spec/` に移す
- [ ] **WSCPUTest v0.7.1、ws-test-suite の採用済みケース、WSTimingTest v0.4.0（pages 0–28）、WSHWTest の `Test All` を全て通す**
- [ ] 公開テスト ROM はリポジトリに同梱せず、環境変数で与えたローカルパスだけをテストハーネスが読む
- [ ] タイルマップ、フレームバッファ、固定メモリ、終了条件を ROM ごとにソース確認して明文化し、推測による判定を行わない
- [ ] 追加の相違が出た場合は、命令トレース、フレーム状態、PCM ハッシュを比較して最初の差分サイクルを特定してから修正する

テスト対象と現時点の判定プロトコルは、元実装の `tests/README.md` と `crates/core/tests/public_roms.rs` を起点に Crystal 側へ移植する。移植途中も Rust 版のテスト総数・公開 ROM の通過ケース数を基準として差分を管理する。

## Crystal らしさを最優先する設計原則

互換性は必須だが、Rust の所有権モデル、trait、`Result`、スレッド設計を Crystal に逐語的に移さない。Crystal の標準ライブラリ、型システム、例外、fiber を生かし、Crystal 開発者が自然に読める・保守できる実装を成功条件の最上位に置く。

- [ ] **標準的な構成と命名**: `src/`、`spec/`、`bin/`、`lib/` の慣例に従う。名前空間とファイルパスを一致させ、型は `PascalCase`、メソッド・変数・ファイル名は `snake_case`、定数は `SCREAMING_SNAKE_CASE` にする。
- [ ] **型を使って状態を表す**: ハードウェア境界の整数は `UInt8` / `UInt16` / `UInt32` など幅を明示する。機種、割り込み、入力、レジスタ種別、実行状態は `enum` と値型を優先し、曖昧な整数フラグや文字列キーを避ける。
- [ ] **責務に合う型を選ぶ**: 小さく値として扱う状態は `struct`、ライフサイクル・可変状態を持つ装置は `class`、名前空間・共有実装は `module` を使う。Rust の trait に相当する複雑な抽象を模倣せず、本当に動的差し替えが必要な境界だけ `abstract class` または小さな module にする。
- [ ] **明快な API**: 失敗が通常の問い合わせ結果である場合は `foo?` と `Nil` を使う。設定不備、壊れたテストデータ、初期化失敗のような例外的な失敗は、意味のある独自 `Exception` を raise/rescue する。ホットパスで例外を制御フローに使わない。
- [ ] **決定論を壊さない並行処理**: コアは同期的な `run_cycles` / `run_frame` API とし、fiber・スレッド・時刻・グローバル可変状態を持ち込まない。フロントエンドで非同期処理が必要な場合だけ、エミュレーション状態の所有者を一つに固定し、`Channel` でコマンドやスナップショットを渡す。共有可変状態、fiber が同じ OS スレッドに戻るという仮定、実験的な並列実行には依存しない。
- [ ] **GC を意識した性能設計**: CPU、PPU、APU、DMA の内側のループでは一時配列、`String`、クロージャ、例外の生成を避ける。固定長バッファと再利用可能な値を使い、速度改善は必ずベンチマークと状態ハッシュで確認する。
- [ ] **安全な FFI**: SDL2 と将来必要な C API は `LibSDL` のような薄い `lib` 宣言に閉じ込める。`Pointer`、未初期化メモリ、ヌルポインタ、寿命管理は安全な Crystal ラッパーで検査してから上位へ公開する。
- [ ] **Crystal 標準の開発体験**: `crystal tool format` と `crystal spec` を常に CI で実行する。spec は振る舞いを短く表し、テーブル駆動の CPU テストには Crystal の配列・named tuple・共有 helper を用いる。メタプログラミングは重複を明確に減らせる場合だけに限定する。

レビューでは「元 Rust コードに似ているか」ではなく、(1) Crystal の慣例に沿うか、(2) 型と API が意図を表しているか、(3) GC と FFI を含めて性能・安全性が説明できるか、(4) 同等性テストを保っているか、の順で判断する。

### Fiber 活用方針

Fiber は UI の応答性を保つための手段として採用候補にするが、ハードウェアの時間モデルには使わない。

- [ ] 最初の SDL2 実装は fiber なしで始め、状態ハッシュと音声遅延を測定する
- [ ] 詰まりが計測された場合だけ、エミュレーション状態を一つの所有 fiber に移す
- [ ] SDL メイン fiber とエミュレーション所有 fiber の間を型付き `Channel` のコマンドで接続する
- [ ] CPU、PPU、APU、DMA、タイマを別々の fiber に分けない
- [ ] fiber 構成の導入前後で、状態ハッシュ、画像、PCM ハッシュの一致を回帰テストで確認する

## 方針変更: Slint を採用しない

Slint は UI 層として採用しない。エミュレータでは画面更新、入力遅延、音声、デバッグ表示を一体で扱う必要があり、UI フレームワークに実行ループを委ねる構成は切り分けが難しいためである。

代わりに、最初の実装では **SDL2 を薄いプラットフォーム層として使う**。

- [ ] ウィンドウ、描画先、ゲームパッド／キーボード入力、音声出力を SDL2 に集約する
- [ ] Crystal の SDL バインディングの機能不足や保守状況に依存しすぎないよう、必要最小限の C FFI をプロジェクト側に置く
- [ ] メニュー、設定、デバッガを初期段階ではキーボード操作とテキストオーバーレイで提供する
- [ ] よりリッチなネイティブ GUI が必要になった時点では、Crystal binding の [UIng](https://github.com/kojix2/uing) を第一候補として検証する

SDL2 は macOS / Linux / Windows で成熟しており、エミュレータに必要な責務を過不足なく満たす。将来 SDL3 へ移す場合も、`Platform` 抽象の内側に変更を閉じ込める。

### 将来のネイティブ GUI: UIng

初期リリースに UIng は依存として追加しない。必要な UI 要件が具体化してから、`frontend/ui` に閉じ込めた検証用実装で採否を決める。

- [ ] UIng が macOS では AppKit、Linux では GTK のネイティブ UI を使えることを検証する
- [ ] UIng の対象を設定、入力割り当て、デバッグツール、ファイル／状態操作などの周辺 UI に限定する
- [ ] ゲーム画面のスケーリング、フレーム提示、ゲームパッド、音声は SDL2 を維持する
- [ ] UIng と SDL2 のイベントループを併用する場合は、macOS / Linux でのウィンドウ所有者、メインスレッド要件、終了処理、入力フォーカス、fiber / Channel の境界を小さな実証アプリで確認する
- [ ] UIng のネイティブ資源の `destroy` / `free` を UI アダプタが一元管理する

## 想定アーキテクチャ

```text
app (CLI / SDL2 frontend)
        │
        ├── platform (window, input, audio, clock, filesystem)
        ├── debug    (overlay, trace, state dump)
        │
        └── emulator_core
              ├── cpu         (V30)
              ├── bus         (memory map, cartridge abstraction)
              ├── video       (tile / sprite / LCD timing)
              ├── audio       (sound channels / samples)
              ├── io          (buttons, RTC, interrupts, DMA)
              └── state       (save state, deterministic snapshots)
```

`emulator_core` は Crystal 標準ライブラリ以外に依存しない。フロントエンドはコアを一定クロックまたは一定フレーム数だけ進め、フレームバッファ、PCM、入力状態を受け渡すだけにする。

実行対象は `ProgramSource` 抽象を介して投入する。製品アプリはリポジトリ内の小さなテストプログラム、または利用許諾が確認できる homebrew データだけとし、ファイル選択画面や汎用 ROM ローダーは設けない。一方、テストハーネスは公開テスト ROM のローカルパスを環境変数から受け取り、元実装と同じオラクルで実行する。

## CI と mise の方針

ローカル開発と CI の検証コマンドを乖離させないため、CI も mise を使う。GitHub Actions の YAML は OS ごとのシステム依存を導入してから `mise run ci` を呼ぶだけにし、ビルド・整形・テストの手順を YAML に重複して書かない。

- [x] `mise.toml` に Crystal と開発ツールの固定バージョン、`format`、`spec`、`build`、`ci` タスクを定義する
- [x] `ci` タスクを `format`、`spec`、`build` の集約タスクにし、ローカルと GitHub Actions の両方で `mise run ci` を実行する
- [x] GitHub Actions では `jdx/mise-action` を固定したバージョンまたはコミットで使用し、mise のツールキャッシュを有効にする
- [x] macOS job では Homebrew、Linux job では apt などを用いて SDL2 と必要な開発ヘッダを明示的に導入する。OS パッケージは mise の管理対象にしない
- [ ] 自作 fixture を使う通常 CI と、ローカル環境変数で公開テスト ROM を与えた opt-in 検証を分離する
- [x] `mise.lock` を導入した場合はリポジトリにコミットし、CI で解決済みバージョンを再現する

Crystal の公式 GitHub Actions ガイドは Crystal の導入方法の参考にするが、プロジェクト固有の検証入口は mise に統一する。

## 段階的な開発計画

- [x] `shard.yml`、`src/`、`spec/`、CI の最小構成を作る。
- [x] macOS で `mise install`、ビルド、ユニットテストを一つのコマンドで実行できる状態にする。
- [x] コーディング規約、エラー方針、ログ形式、ライセンス方針を `docs/` に記録する。

完了条件: 新しい macOS 環境で、mise だけを前提に空のアプリとテストを再現可能にビルドできる。

### 1. コアの最小実行系

- [ ] V30 のレジスタ、命令デコーダ、フラグ、メモリアクセスを実装する。
- [ ] 元実装の命令単位テストを Crystal の spec に 1 対 1 で移す。
- [ ] バス、メモリマップ、割り込みコントローラ、タイマを実装する。
- [x] 1 命令ごとのトレースと、再現可能なスナップショットを用意する。

完了条件: ヘッドレスの自作テストプログラムが期待するレジスタ値、メモリ値、割り込み順序を示し、WSCPUTest の全項目を通過する。

### 2. 映像と入力

- [ ] LCD タイミング、背景、タイル、スプライト、パレットを段階的に実装する。
- [ ] まず単色 WonderSwan、続いて Color / Crystal の拡張を追加する。
- [ ] コアから RGBA フレームバッファを取得する API を固定する。
- [ ] SDL2 フロントエンドで画面表示、整数倍率、キーボード／ゲームパッド入力を実装する。
- [ ] フレームごとの画像比較テストを用意する。

完了条件: macOS 上で自作の画面・入力検証プログラムを 60 fps 相当で表示でき、期待画像との差分を CI で検出できる。

### 3. 音声、保存、デバッグ機能

- [ ] 音源、音声タイミング、SDL2 のオーディオキューを実装する。
- [ ] フレーム同期と音声バッファを調整し、音切れ・入力遅延を測定する。
- [ ] セーブステートをバージョン付きの自前形式で実装し、保存先をテスト・設定データに限定する。
- [ ] 一時停止、単一命令実行、メモリ表示、CPU トレース、画面レイヤー表示をオーバーレイで提供する。

完了条件: ヘッドレスと GUI 実行で同じ状態遷移を再現し、音声テストの波形ハッシュが安定する。

### 4. プラットフォーム展開

- [ ] **macOS**: SDL2 の導入手順、署名なし開発ビルド、Apple Silicon / Intel の確認を完了する。
- [ ] **Linux**: Ubuntu LTS を基準に、Wayland / X11 の両方で起動・入力・音声を確認する。
- [ ] macOS / Linux で同一のヘッドレス統合テスト、画面スナップショットテスト、起動確認を CI で実行する。

Windows は Crystal が Windows を正式サポートしてから、別フェーズとして計画する。それまでは `x86_64-windows-msvc`、MinGW-w64、MSYS2、Windows 専用 CI、DLL 同梱を試行しない。正式化後は元 Swanium と同じ MSVC 経路を第一候補として、最小 SDL2 アプリと全公開テスト ROM の通過から検証を始める。

完了条件: macOS と Linux の配布物が同じ検証プログラムを同じ状態ハッシュまで実行し、公開テスト ROM の採用済みケースをすべて通過する。

### 5. 品質と公開準備

- [ ] パフォーマンス測定を自動化し、標準設定で実時間より十分速く動作することを確認する。
- [ ] 状態破損、異常入力、未対応機能を安全に報告する。
- [ ] 対応状況を「ハードウェア機能単位」で `docs/compatibility.md` に公開する。商用タイトル単位の互換性表は作らない。
- [ ] ビルド手順、利用可能なテストプログラム、制限事項、ライセンスを README にまとめる。

## テスト戦略

- [ ] **ユニットテスト**: CPU 命令、フラグ、メモリマップ、タイマ、割り込み、描画プリミティブを検証する。
- [ ] **統合テスト**: 自作プログラムを決めたサイクル数実行し、CPU 状態・RAM・VRAM・音声ハッシュを照合する。
- [ ] **移植同等性テスト**: Rust 版と同じユニット／統合ケースを実行し、公開 ROM は元実装と同じ入力、起動方法、合否オラクルで照合する。
- [ ] **リグレッションテスト**: PNG フレームと PCM ハッシュを保存し、意図的に更新する場合だけレビューする。
- [ ] **差分調査**: 命令トレースとフレーム単位スナップショットを出力して、最初に異なるサイクルを特定する。
- [ ] **手動確認**: 実 OS ごとのウィンドウ、ゲームパッド、音声デバイス切替、サスペンド復帰を確認する。

テスト用データはすべて自作、または再配布が明確に許可されたものに限定する。

## 主要なリスクと対策

| リスク | 対策 |
| --- | --- |
| Crystal の FFI 差異 | SDL 呼び出しを `platform/sdl` に隔離し、少数の API だけを手書きバインドする。 |
| 描画タイミングの不正確さ | 描画を段階実装し、フレーム比較とサイクル単位トレースで検証する。 |
| OS ごとの入力・音声差 | macOS で API を固め、Linux / Windows は同じ受け渡し API に適合させる。 |
| テストデータの権利問題 | 実 ROM を扱わず、自作または許可済みデータだけを CI に置く。 |
| UI 機能の肥大化 | まず SDL2 とオーバーレイに限定し、設定 UI は要件が固まってから追加する。 |
